# T4 統整：Agent 與 harness

2026-11-11，T4／T5 工作階段。來源與篩選過程見 [search-log/T4.md](../search-log/T4.md)。

用語：
- **harness（外殼）**：模型外面那一整套讓它能當 agent 的東西，包括提示詞、工具、記憶、流程控制。模型權重不變，只改外殼。
- **workflow（固定流程）**：步驟由程式事先寫死，模型只在每一步做指定的工作。
- **agent（自主代理）**：模型自己決定下一步做什麼、用哪個工具、何時結束。
- **預填（prefill）**：模型開始回答前，先把整段提示讀過一遍的計算；提示越長越久。讀過的開頭部分會被快取，下一輪開頭相同就幾乎不用再算。

## 1. 問題與結論摘要

| 問題 | 結論 |
|---|---|
| 三條路怎麼選？ | **自己寫一個薄的、由程式控制流程的 harness**，直接呼叫 Ollama 的 `/api/chat`（`tools`、`format`、`think` 三個參數）。現成外殼留作對照組，不當主體；框架只在需要時借零件（例如資料驗證、介面）。理由見第 3、4 節。 |
| harness 由哪些元件組成？ | 可用 harness2 的 8 個元件當分類：系統提示、護欄、記憶、技能、工具說明、腳本、子代理、外掛（中介層）。它們分屬四個功能：決定模型看到什麼（上下文）、工具介面、分工協調、在工具迴圈中強制執行規則。 |
| harness2 的方法能不能用本地模型跑？ | **現成程式不能**：綁 Linux、Google Cloud、Vertex AI，評審和改良器只支援雲端模型，每題的運算量以百萬 token 計。**方法可以手動借用**：用自己的評估題組，「提出修改 → 同一組題目重跑 → 比較行為 → 有證據才採用」，執行者是 qwen3.5:9b，改良者是我（要不要讓 frontier 模型在開發期提改良建議，見第 4 節第 4 條，需要使用者決定）。 |

## 2. 別人怎麼做

### 2.1 做 agent 的三條路

1. **自己寫**：Anthropic 建議先直接用 API，很多模式幾行程式就能做；框架的抽象層會讓提示和回應難除錯（[筆記](../notes/web/2024-anthropic-building-effective-agents.md)）。Ollama 官方文件的 agent 迴圈範例就是一個 `while` 迴圈（[筆記](../notes/web/2026-ollama-tool-calling-structured-outputs.md)）。HumanLayer 的 12-factor agents（C 級）也主張「自己掌握控制流程」「小而專注的 agent」。
2. **現成外殼**：`ollama launch` 一鍵接 Claude Code、Codex、OpenCode、Qwen Code、Hermes Agent、OpenClaw、DeepSeek Harness、Cline 等（[筆記](../notes/web/2026-ollama-launch-integrations.md)）。它們大多是寫程式用的終端機 agent，或接訊息 App 的個人助理。
3. **框架**：Qwen 官方的 Qwen-Agent（模型卡推薦，[筆記](../notes/repos/QwenLM-Qwen-Agent.md)），以及 smolagents、LangGraph、PydanticAI、LlamaIndex、DSPy（只篩選，見 search-log）。

### 2.2 harness 的元件

- **harness2**（[筆記](../notes/repos/google-research-harness2.md)）的 8 個元件，每個是一個檔案：

  | 功能 | 元件 | 何時進入模型 |
  |---|---|---|
  | 上下文 | 系統提示、護欄（硬規則）、長期記憶 | 每次呼叫 |
  | 上下文 | 技能（特定程序的說明） | 用到才載入 |
  | 工具介面 | 工具說明 | 每次呼叫 |
  | 工具介面 | 腳本（確定性程式，取代讓模型逐字推理） | 經 bash 執行 |
  | 分工 | 子代理（在自己的上下文做事，只回傳結果） | 委派時 |
  | 中介層 | 外掛（包在工具呼叫外，強制行為） | 每次工具呼叫 |

- **其他說法**：Meta-Harness 把 harness 定義為「決定要儲存、檢索、呈現什麼資訊給模型的程式」；Anthropic 的「增強 LLM」＝ 模型 ＋ 檢索、工具、記憶，再用 workflow 模式組合；Anthropic 的 context engineering 文章把上下文當有限的「注意力預算」，手段是壓縮歷史、結構化筆記、子代理（Meta-Harness 與 context engineering 只篩選）。
- harness2 個案的共同教訓：失敗多半是程序問題（沒交叉核對、寫完不檢查、把工具呼叫寫成文字而沒執行），修法是護欄、技能、檢查腳本，而不是補知識。

## 4. 對 AI TA 的建議

1. **主體用自己寫的「程式控制流程」harness，不用現成外殼當主體。**
   - 根據：複習流程（找弱點 → 出題 → 批改 → 解釋 → 排程）步驟固定，符合 Anthropic「能乾淨拆成固定子任務就用 workflow」的條件；NVIDIA 立場論文的「程式主導」架構也主張讓控制程式協調、小模型只做窄的語言工作（[筆記](../notes/papers/2025-slm-future-agentic.md)）。
   - 狀態：**已確認**（Anthropic、NVIDIA 兩個獨立的 B 級來源一致）；但沒有「同一個 9B、固定流程 vs 自主 agent」的直接對照研究，在 AI TA 上的效果是**推論**，要靠評估驗證。
2. **現成外殼只當評估時的對照組（例如「qwen3.5:9b ＋ Qwen Code」），而且要先問使用者才能安裝。**
   - 根據：外殼為寫程式設計；官方一律建議 64k 上下文，本機預設 32k（Ollama 文件＋本機 `ollama ps`）；Codex 的基本指示就 4,589 token，冷啟動預填 17 秒，14.6k token 要 58 秒（本機實驗 E3）。
   - 狀態：上下文需求**已確認**（官方文件＋本機量測）；外殼對 9B 正確率的影響**查不到**（沒有任何外殼搭配 9B 的評估）。本機實驗 E3b（Codex 提示＋30 個工具＋AI TA 規則）在 3 種簡單情況 9/9 選對工具，表示「人設不合」在簡單情況不致命，但成本是延遲（**單一來源**：本機實驗，樣本小）。
3. **用 harness2 的 8 元件當 `dev/harness/` 的檔案分類，每個元件一個純文字檔，改動就是 diff。**
   - 對應（推論）：系統提示＝助教人設與引用規則；護欄＝「只根據講義回答、查不到要說」；記憶＝學習者弱點（T6）；技能＝出題、批改、解釋各自的步驟說明；工具說明＝每個工具何時用；腳本＝JSON 驗證、出處檢查、排程演算法（T3／T6）；子代理＝先不用；外掛（中介層）＝驗證失敗就重試、記錄每次呼叫。
   - 狀態：拆法本身是**單一來源**（harness2 沿用 AHE，同一脈絡）；套到 AI TA 是**推論**。
4. **「改良外殼」用 harness2 的方法手動做：評估題組就是「同一題重跑」的試跑場。**
   - 做法（推論）：每次只改一個元件 → 用同一組期中題目重跑 → 看行為差異（答對率、出處正確、長度、延遲）→ 有證據才保留，並記下原因（對應 harness2 的 `EXPERIENCE.md`）。
   - **待使用者決定**：harness2 的改良者是 frontier 模型。`docs/plan.md` 只說 frontier 模型「只在評估時使用，AI TA 執行時不依賴它」，沒說開發期能不能用它來提改良建議；這會影響「AI TA 的提升有多少來自 frontier 模型」的說法，對外報告時要講清楚。
   - 狀態：方法有效是 harness2 作者自測（**單一來源**，而且只測大型雲端模型）；能否用在 9B **查不到**。
5. **框架只借零件，不讓框架掌控流程。**
   - 根據：Anthropic 指出框架的抽象層會讓除錯變難；Qwen 官方文件承認工具呼叫格式不保證遵守，程式必須自己準備補救（[Qwen-Agent 筆記](../notes/repos/QwenLM-Qwen-Agent.md)）。可以借的零件：Pydantic 驗證輸出、需要快速介面時用 Qwen-Agent 的 `WebUI` 或 Gradio（介面另見 T7）。
   - 狀態：**單一來源**（Anthropic 的經驗性建議）＋**推論**。
