# T5 統整：小模型做 agent

2026-11-11，T4／T5 工作階段。來源與篩選過程見 [search-log/T5.md](../search-log/T5.md)；本機實驗見 [筆記](../notes/internal/2026-local-qwen35-tool-calling.md)。

用語：
- **工具呼叫（function calling）**：模型不直接回答，而是輸出「要呼叫哪個函式、參數是什麼」，由程式執行後把結果交回模型。
- **結構化輸出**：要求模型輸出符合指定格式（JSON schema）的資料，讓程式能直接讀。
- **單輪／多輪**：單輪是一次輸入就決定一個呼叫；多輪是要根據前面的結果、跨好幾步完成任務。
- **預填**：模型讀提示的計算，提示越長越久（T4 統整有說明）。

## 1. 問題與結論摘要

| 問題 | 結論 |
|---|---|
| 7–9B 的工具呼叫穩不穩？ | **單輪穩、多輪不穩**。BFCL 排行榜上 Qwen3-8B 的單輪分數和第 1 名相當，但多輪、網路搜尋、記憶遠低於頂尖模型。本機 qwen3.5:9b 的單步驟工具決定 96 次中 93 次正確，錯的 3 次都是**不呼叫工具卻說「已記錄」**。 |
| 結構化輸出可靠嗎？ | **格式可以靠 `format` 保證，內容要另外驗證**。本機 13 次全部合法、答案正確；研究顯示嚴格格式可能傷推理，但這點有爭議；兩邊都同意「先推理、後填答案」。 |
| 固定流程還是自主規劃？ | **固定流程較適合小模型**。間接證據一致（小模型多輪弱、拆角色有效、固定流程勝過複雜 agent、程式主導的架構），但**沒找到**同一個 7–9B 模型「固定流程 vs 自主 agent」的直接對照。 |
| 驗證迴圈有用嗎？ | **要有外部依據才有用**。叫模型「再檢查一次」會把對的改錯（越弱的模型越嚴重）；對照講義、標準答案、程式規則的檢查才有效。 |
| 專門針對工具呼叫的微調？ | **有效但不是第一步**。微調能讓 7B 從 41% 升到 83%（TinyAgent，自測）、讓 8B 的多輪分數超過頂尖模型（xLAM-2-8b，BFCL 排行榜）；但要大量合成資料和算力，Mac 上可不可行見 T6。 |
| 現成外殼對 9B 太重嗎？ | **延遲上是，正確率上未證實**。官方建議 64k 上下文（本機預設 32k）；Codex 的基本指示 4,589 token 冷啟動預填 17 秒，29k token 要 126 秒；但在 30 個工具＋Codex 提示下，簡單的單步驟決定仍然選對。 |

## 2. 別人怎麼做（五類解法）

1. **縮小每一步的問題**：讓程式控制流程、模型每次只做一個決定。例：α-UMi 把規劃、呼叫、總結拆給三個小模型（[筆記](../notes/papers/2024-small-llms-weak-tool-learners.md)）；TinyAgent 讓模型一次產生「函式呼叫計畫」再由程式執行（[筆記](../notes/papers/2024-tinyagent.md)）；ReWOO 先規劃後執行；Agentless 用固定三步驟；NVIDIA 的「程式主導」架構（[筆記](../notes/papers/2025-slm-future-agentic.md)）。
2. **縮小工具與上下文**：只放需要的工具（TinyAgent 的 Tool RAG、Less is More、RAG-MCP）；把上下文當有限資源（Anthropic context engineering）；指令越多遵循率越低（IFScale）。
3. **約束輸出**：用模型原生的工具呼叫格式，不用停止詞式的 ReAct 範本（Qwen 官方，[筆記](../notes/repos/QwenLM-Qwen-Agent.md)）；JSON schema 結構化輸出加驗證（[Ollama 筆記](../notes/web/2026-ollama-tool-calling-structured-outputs.md)）；推理和格式分開（[Let Me Speak Freely](../notes/papers/2024-let-me-speak-freely.md)）。
4. **有外部依據的驗證**：工具回饋（CRITIC）、標準答案、程式檢查；避免無依據的自我修正（[筆記](../notes/papers/2024-llms-cannot-self-correct.md)）。
5. **微調**：合成工具呼叫資料後微調（TinyAgent、α-UMi、ToolACE、APIGen／xLAM、Hammer）。

## 4. 對 AI TA 的建議

1. **流程由程式控制，模型每一步只做一個單輪決定；不讓 9B 自主規劃整段複習。**
   - 根據：BFCL 排行榜上 8B 級單輪接近頂尖、多輪落後（[筆記](../notes/papers/2025-bfcl.md)）；α-UMi 顯示一個小模型身兼規劃、呼叫、總結會顧此失彼；ReAct 顯示小模型只靠提示學不會邊想邊做。
   - 狀態：「小模型多輪自主決策較弱」**已確認**（BFCL 與 α-UMi、ReAct 是不同團隊、不同年代的結果）；「固定流程在 AI TA 上優於自主 agent」是**推論**，沒有直接對照研究。
2. **每一步只放這一步需要的 1–3 個工具，能由程式決定的事就不交給模型。**
   - 例：「記錄作答對錯」可以讓使用者直接按按鈕、由程式寫入，不需要模型呼叫 `record_answer`。
   - 根據：TinyAgent 只放需要的工具，提示少一半、正確率還略升；Less is More 說減少工具能提升表現、執行時間最多減少 70%；Anthropic 點名「工具太多」是常見失敗。本機 E2 在 30 個工具下簡單情況沒變差，但多了約 1,670 token、冷啟動多 8 秒。
   - 狀態：「工具少而精較好」**已確認**（TinyAgent〔A〕與 Less is More〔DATE 2025〕兩個獨立的同儕審查來源）；「30 個工具在簡單情況不影響 qwen3.5:9b 正確率」是**單一來源**（本機實驗，樣本小）。
3. **防「假的成功訊息」：工具真的執行成功後，才由程式告訴使用者結果。**
   - 根據：本機實驗預設取樣下 23 次有 3 次「沒呼叫卻說已記錄」；社群在 MLX runner 上也回報同樣現象（[ollama#14493](https://github.com/ollama/ollama/issues/14493) 的留言，C 級）；harness2 的個案也有「把呼叫寫成文字沒執行」。
   - 狀態：**已確認**有這種失敗（本機實驗與社群回報彼此獨立，但都不是高等級來源）；發生頻率**查不到**可靠數字。
4. **工具呼叫和結構化輸出的步驟，覆寫 Ollama 的預設取樣，並在提示寫明「何時一定要呼叫哪個工具」。**
   - 根據：Ollama 預設 temperature 1；模型卡的「不思考、一般任務」建議 temperature 0.7、top_p 0.8；Ollama 文件建議結構化輸出用 0；本機 E5 調低溫度或加規則後 25 次沒有再出錯。
   - 狀態：建議值本身是**單一來源**（Qwen 官方）；「調低後假成功消失」是**單一來源**（本機實驗，樣本小）。
5. **結構化輸出：`format` 加 schema，同時把 schema 寫進提示，再用 Pydantic 驗證；需要推理的欄位放前面，或讓推理留在思考模式／先自然語言回答再轉格式。批改結果（對錯、錯誤類型）這種分類輸出可以用嚴格 schema。**
   - 根據：Ollama 官方建議；Let Me Speak Freely（格式限制傷推理、幫分類；推理在前）；本機 E4。
   - 狀態：「嚴格格式會傷推理」**互相矛盾**（EMNLP 2024 論文 vs .txt 廠商反駁，差別在提示設計）；「推理在前、答案在後」兩邊都同意。
6. **驗證迴圈只用外部依據：講義原文、標準答案、程式可檢查的規則；不要叫模型「再檢查一次」。**
   - 根據：Huang et al.（ICLR 2024）沒有外部回饋時自我修正全面變差，Llama-2 有 31% 把對的改錯；CRITIC（ICLR 2024）有工具回饋時自我修正有效。
   - 狀態：**已確認**（兩篇 ICLR 2024 論文，不同團隊，結論互補）。
7. **思考模式按步驟開關。**
   - 根據：本機實驗 E1：工具決定開思考 12/12、不開 18/20，但生成時間約 3–5 倍；出題開思考慢約 10 倍、品質看不出差別。模型卡則說思考模式要 128K 上下文才能發揮，本機預設 32k。
   - 狀態：**單一來源**（本機實驗，樣本小）；32k 對思考品質的影響**查不到**。
8. **工具呼叫微調列為後期選項，先把 harness 做好、收集互動紀錄。**
   - 根據：微調有效（TinyAgent、α-UMi、xLAM-2-8b），但 TinyAgent 用了 8 萬筆合成資料，α-UMi 要全參數微調；NVIDIA 建議先記錄 agent 的每次呼叫，累積 1 萬到 10 萬筆後再微調。Mac 上微調 9B 的可行性見 T6（[mlx-lm](../notes/repos/ml-explore-mlx-lm.md)、[QLoRA](../notes/papers/2023-qlora.md)）。
   - 狀態：「微調能大幅提升小模型工具呼叫」**已確認**（TinyAgent 與 α-UMi 兩篇同儕審查論文，皆作者自測；BFCL 排行榜的 xLAM-2-8b 是第三方測量）；對 qwen3.5:9b 是否還需要**查不到**。
9. **不要把 AI TA 做成「現成外殼＋9B」。**
   - 根據：見 [T4 統整](T4.md)。官方建議 64k 上下文、本機預設 32k；冷啟動預填 4.6k token 要 17 秒；生成約每秒 10 token。
   - 狀態：延遲與上下文**已確認**（官方文件＋本機量測）；對正確率的影響**查不到**。

## 5. 還不知道的事

- **同一個 9B 模型、固定流程 vs 自主 agent** 在複習任務上的差距：沒找到研究，可以在第 5–7 步用評估題組自己比。
- **qwen3.5:9b 的多輪可靠度**：本機只測單步驟；可以參考 τ-bench 的 pass^k（同一題重跑 k 次都成功的比例）設計多輪測試。
- **32k 與 128k 上下文對思考品質的影響**：模型卡建議 128K，本機預設 32k；`num_ctx: 65536` 在 API 設定後 `ollama ps` 仍顯示 32768，原因未查明。
- **生成速度**：本機量到約每秒 10 token，比基準紀錄推算的慢，原因未知；影響互動體驗的估計。
- **renderer 的影響**：社群回報換成 `qwen3-coder` renderer 能減少假成功（舊版 Ollama）；0.40.10 已改用 XML 格式，是否還需要沒測（要用 `ollama create` 建新模型設定，屬於改設定，先問使用者）。
- **工具說明用中文還是英文**比較好：本機只用中文說明，沒有比較。
